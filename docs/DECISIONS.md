# Decisions

Appended at the moment a decision was made, not reconstructed afterwards. An
entry earns its place when a check rejected something and the content changed
rather than the check, when an instruction was declined because it contradicted
an earlier decision, when a bug that rendered with no error was made impossible,
or when a conflict with the fixed starter layer had to be routed around.

"How I knew" is never "the checks passed" — it is the read, run or comparison
done before accepting the change.

## 2026-09-19 — A chart that never once rendered in its own colours
Commit: bf5f5cd
Obvious option: Treat the dispatch console's invisible dark-mode chart as a dark-mode defect and give the series per-theme values. That is what it looked like: the chart reads on cream and disappears on near-black, which is the signature of a palette that was only ever tuned for one ground.
Why not that: The palette was never the problem. Astro compiles a component's scoped CSS by appending an attribute selector, so `.dc-supply` becomes `.dc-supply[data-astro-cid-xxxxxx]`. An element created in the client script with createElementNS carries no such attribute, so the rule never matched, and an unmatched SVG element does not render unstyled in any visible sense — it falls back to fill: black. The dispatch console's four stack layers have therefore never rendered in the colours its own legend claims, on any build since 28086c7. The server-rendered parts were correct the whole time; the chart they described was not. Changing the palette would have painted over a chart that was not reading the palette at all.
How I knew the result was right: The dividing line is exact and checkable. Every class the components assign in script — dc-supply, dc-storage, dc-reserve, dc-short, dc-soc-line, the three dc-mark classes, sz-mark, sz-mark-label, dial-worst-mark, dial-worst-label — had a scoped rule and rendered black. Every class present in the server-rendered markup — sz-deficit, sz-cover, dial-tick — rendered correctly. And `.trough` is the control case: it is declared inside CourseChrome's `<style is:global>` as a shared convention, and it is the one script-created element in the dial that has always looked right. Wrapping the affected selectors in :global() turned every measured fill from 0,0,0 into the declared colour, and the unserved layer now inverts across themes as intended, 220,38,38 on light and 248,113,113 on dark.
What it says about the harness: it passed everything. Sixty-six tests, axe on thirty pages, and four rounds of visual review by two people. On a cream ground a black chart reads as a deliberately inked one, so the defect looked like a design decision, and every reviewer including me confirmed it by eye. Dark mode did not create it — it removed the camouflage that had been hiding it. axe could not see it either: black on cream has excellent contrast, and the rule the chart broke was not an accessibility rule but an agreement between a chart and its own stylesheet.
The check that now exists asserts the cause rather than the symptom, because the symptom is not reachable from this suite: the elements do not exist until the client script runs, there is no SVG layout in the test environment, and a headless browser would be a new dependency. So check:instrument-styling asserts statically that any class a component both assigns in script and styles in its own block must be declared :global(). Verified by reverting each of the four :global() wrappers in turn and watching it fail.
And a note on the measuring, because it is part of the same lesson. The first contrast harness reported fourteen failures. Nearly all were false: its regex read `oklch(0.2 0.01 72.95 / 0.78)` and treated 0.2, 0.01 and 72.95 as red, green and blue, so every oklch token collapsed to 1.00:1 and only the literal rgb() values appeared to pass. It was caught before anything was reported, and the harness was rebuilt to resolve colours through a canvas in the page so that oklch, color() and alpha all composite correctly. The second harness then reported the console failures, and those were real. A measurement instrument is a claim too, and it needs the same provenance as any other number on this site. The check written above then found its own version of the same fault on its first run — it read a CSS comment mentioning `.trough` as a declaration of `.trough`, because it did not strip comments before parsing. A parser that reads its own prose as data is the same error one layer up.
